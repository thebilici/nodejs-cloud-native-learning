# Bugün ne yaptım?

## Docker Network kavramını öğrendim

Docker Network’ün container’ların birbirleriyle ağ üzerinden haberleşmesini sağladığını öğrendim.

Container IP adreslerinin dinamik olarak değişebileceğini gördüm.

Bu nedenle servis adreslerini kaynak kod içinde IP olarak sabitlemenin doğru olmadığını öğrendim.

Docker, aynı custom network üzerindeki container’ların birbirlerini isimleriyle bulabilmesi için dahili DNS sağlar.

Temel mantık:

```text
Container adı
      │
      │ Docker DNS
      ▼
Container IP adresi
```

Bu sayede servisler IP adresi yerine sabit ve okunabilir isimler kullanabilir.

---

## Mevcut Docker networklerini inceledim

Şu komutu kullandım:

```powershell
docker network ls
```

Görüntülenen networkler:

```text
bridge
host
kind
none
```

Şunları öğrendim:

- `bridge`, Docker’ın varsayılan network türüdür.
- `host`, container’ın host network alanını kullanmasını sağlar.
- `none`, container’ın network erişimini kapatır.
- `kind`, daha önce oluşturulan Kubernetes kind cluster tarafından kullanılır.

`kind` networküne müdahale edilmedi.

---

## Custom bridge network oluşturdum

Service A ve Service B için ortak bir network oluşturdum:

```powershell
docker network create cloud-native-network
```

Oluşturulan network:

```text
cloud-native-network
```

Networkü kontrol etmek için:

```powershell
docker network ls
docker network inspect cloud-native-network
```

komutlarını kullandım.

İlk oluşturulduğunda network içinde herhangi bir container bulunmuyordu:

```json
"Containers": {}
```

## Service A containerını custom networke bağladım

Service A containerını yeniden oluşturarak custom networke bağladım:

```powershell
docker run -d `
  --name service-a-container `
  --network cloud-native-network `
  -p 3000:3000 `
  service-a:1.0
```

Buradaki:

```text
--network cloud-native-network
```

parametresinin containerın hangi Docker Network üzerinde çalışacağını belirlediğini öğrendim.

Network verilmezse containerın varsayılan bridge networke bağlandığını öğrendim.

---

## Container içindeki `localhost` kavramını öğrendim

Container içindeki `localhost` adresinin host bilgisayarı veya başka bir containerı değil, containerın kendisini ifade ettiğini öğrendim.

Örneğin Service A containerı içinde:

```text
localhost
=
service-a-container
```

Bu nedenle Service A içinden Service B’ye ulaşmak için şu adres kullanılamaz:

```text
http://localhost:3001
```

Çünkü bu adres Service A containerının kendi `3001` portunu ifade eder.

Doğru yaklaşım:

```text
http://service-b-container:3001
```

şeklinde hedef containerın DNS adını kullanmaktır.

---

## Docker DNS iletişimini geçici curl containerıyla test ettim

Aynı network üzerinde geçici bir curl containerı çalıştırdım:

```powershell
docker run --rm `
  --network cloud-native-network `
  curlimages/curl:latest `
  -s http://service-a-container:3000/health
```

Bu testte:

- IP adresi kullanılmadı.
- `localhost` kullanılmadı.
- Container adı kullanıldı.
- Docker DNS, `service-a-container` adını container IP adresine çözdü.
- Service A’nın `/health` endpointinden başarılı JSON cevabı alındı.

Test akışı:

```text
Geçici curl containerı
          │
          │ Docker DNS
          ▼
service-a-container
          │
          ▼
GET /health
```

`--rm` parametresinin geçici containerı işlem tamamlandıktan sonra otomatik olarak sildiğini öğrendim.

`curl` komutundaki `-s` parametresinin progress bilgisini gizleyerek yalnızca response gövdesini gösterdiğini öğrendim.

# Servisler arası iletişim

## Service A’ya Service B çağrısı eklendi

Service A içinde şu handler oluşturuldu:

```text
services/service-a/src/handlers/call-service-b.handler.ts
```

Handlerın görevi:

- Client’tan gelen isteği karşılamak
- Service B’ye HTTP isteği göndermek
- Service B’den gelen cevabı okumak
- Sonucu client’a döndürmek

Handler ilk olarak yanlışlıkla Service B içinde oluşturuldu.

Daha sonra doğru servis olan Service A içine taşındı.

Şunu öğrendim:

> Servis çağrısını başlatan handler, çağrıyı yapan servisin içinde bulunmalıdır.

---

## Node.js `fetch()` API’sini öğrendim

Service A’dan Service B’ye HTTP isteği göndermek için Node.js’in yerleşik `fetch()` API’si kullanıldı.

Örnek:

```typescript
const response = await fetch(`${serviceBUrl}/hello`);
```

Bu satır şu HTTP isteğini gönderir:

```text
GET http://service-b-container:3001/hello
```

Şunları öğrendim:

- `fetch()` varsayılan olarak GET isteği gönderir.
- HTTP işlemi asenkron olduğu için `await` kullanılır.
- `await` kullanılan fonksiyon `async` olmalıdır.
- `fetch()` doğrudan JSON nesnesi değil, HTTP `Response` nesnesi döndürür.
- Response body şu şekilde okunur:

```typescript
const data = await response.json();
```

---

## Service B adresini environment variable olarak verdim

Service A `.env` dosyasına şu değer eklendi:


Bu değer Service B’ye değil, Service A’ya aittir.

Çünkü Service B adresini bilmesi gereken taraf isteği gönderen Service A’dır.

Şunu öğrendim:

> Hedef servis adresi, isteği gönderen servisin yapılandırmasıdır.
