## Container çalışma dizinini oluşturdum

```dockerfile
WORKDIR /app
```

satırıyla container içindeki çalışma dizinini `/app` olarak belirledim.

Şunları öğrendim:

- `/app` klasörü Windows üzerindeki `C:\app` klasörü değildir.
- `/app`, Docker'ın yönettiği Linux tabanlı container dosya sistemi içinde bulunur.
- Sonraki Dockerfile komutları bu klasörü esas alır.

---

## Package dosyalarını image içine kopyaladım

```dockerfile
COPY package*.json ./
```

satırıyla:

- `package.json`
- `package-lock.json`

dosyalarını image içindeki `/app` klasörüne kopyaladım.

`package*.json` kalıbındaki `*` karakterinin iki package dosyasını da kapsadığını öğrendim.

---

## Docker cache mantığını öğrendim

Kaynak koddan önce package dosyalarını kopyalamanın neden önemli olduğunu öğrendim.

Eğer package dosyaları değişmezse Docker:

```dockerfile
RUN npm install
```

katmanını cache üzerinden tekrar kullanabilir.

Böylece her kaynak kod değişikliğinde bağımlılıklar yeniden kurulmaz.

Bu yaklaşım:

- Build süresini azaltır.
- Ağ kullanımını azaltır.
- Docker layer cache kullanımını iyileştirir.

---

## Bağımlılıkları image içinde kurdum

```dockerfile
RUN npm install
```

satırıyla bağımlılıkları image build aşamasında kurdum.

Şunları öğrendim:

- `RUN`, image build edilirken çalışır.
- Express, npm'in içinde bulunan bir kütüphane değildir.
- Express ve diğer paketler npm registry üzerinden indirilir.
- Bağımlılıklar image içindeki `/app/node_modules` klasörüne kurulur.
- Aynı image'dan birden fazla container oluşturulduğunda `npm install` tekrar çalışmaz.

## `.dockerignore` oluşturdum

Service A klasöründe `.dockerignore` dosyası oluşturdum.

İçeriği:

```dockerignore
node_modules
dist
.env
.git
.gitignore
npm-debug.log
```

Şunları öğrendim:

- `.gitignore`, Git tarafından takip edilmeyecek dosyaları belirler.
- `.dockerignore`, Docker build context içine alınmayacak dosyaları belirler.
- `.env` Git tarafından takip edilmese bile `.dockerignore` içinde yoksa Docker build context'ine girebilir.
- Host üzerindeki `node_modules` klasörünü Linux tabanlı image içine kopyalamak doğru değildir.
- `.env` dosyasını image içine gömmek güvenlik ve ortam bağımsızlığı açısından yanlış bir yaklaşımdır.

## TypeScript kodunu build ettim

Yerel ortamda şu komutu kullandım:

```powershell

```

Bu komut package script'i üzerinden `tsc` çalıştırdı.


akışı gerçekleşti.

`dist` klasöründe şu dosyaların oluştuğunu doğruladım:

- `dist/server.js`

- `dist/handlers`
- `dist/routes`
- `dist/workload`

Şunları öğrendim:

- `src`, TypeScript kaynak kodunu içerir.
- `dist`, derlenmiş JavaScript çıktısını içerir.
- `dist` içindeki dosyalar elle düzenlenmez.
- Kaynak kod değişiklikleri `src` altında yapılır.

## Container başlangıç komutunu tanımladım

```dockerfile

```

satırıyla container başladığında çalışacak ana komutu belirledim.

`npm start`, package script'i üzerinden şu komutu çalıştırdı:

```text

```

`RUN` ile `CMD` arasındaki farkı öğrendim:

```text

```

## Docker image oluşturdum

Build işlemi sırasında Buildx'in `docker-container` driver kullandığını gördüm.

İlk build sonucunda şu uyarıyı aldım:

```text
No output specified with docker-container driver.
Build result will only remain in the build cache.
```

Build sonucunu yerel Docker image store'a yüklemek için `--load` kullanılması gerektiğini öğrendim.

Kullandığım komut:

```powershell
docker buildx build --load -t service-a:1.0 .
```

Oluşan image'ı şu komutla doğruladım:

```powershell
docker images service-a
```

Oluşan image:

```text
service-a:1.0
```

---

## Container oluşturdum

Image'dan container oluşturmak için şu komutu kullandım:

```powershell
docker run --name service-a-container -p 3000:3000 service-a:1.0
```

Şunları öğrendim:

- `docker run`, image'dan yeni bir container oluşturur ve çalıştırır.
- `--name`, container'a okunabilir bir isim verir.
- `-p`, host portu ile container portunu eşleştirir.
- Port mapping formatı `HOST_PORT:CONTAINER_PORT` şeklindedir.

Bu projede:

```text
localhost:3000
↓
container:3000
```

eşleştirmesi yapıldı.

## Container yaşam döngüsünü öğrendim

Kullandığım komutlar:

```powershell
docker ps
docker ps -a
docker logs service-a-container
docker stop service-a-container
docker start service-a-container

```

Şunları öğrendim:

- `docker ps`, yalnızca çalışan container'ları gösterir.
- `docker ps -a`, çalışan ve durmuş bütün container'ları gösterir.
- `docker stop`, container'ı durdurur fakat silmez.
- `docker start`, durmuş mevcut container'ı yeniden çalıştırır.
- `docker run`, image'dan yeni bir container oluşturur.
- `docker rm`, container'ı siler.
- Container silinse bile image sistemde kalmaya devam eder.
- Aynı image'dan birden fazla bağımsız container oluşturulabilir.

# Karşılaştığım problemler

## Problem 1 — Build sonucu image listesinde görünmedi

### Hata veya uyarı

```text
No output specified with docker-container driver.
Build result will only remain in the build cache.
```

### Sebep

Aktif Buildx builder `docker-container` driver kullanıyordu.

Bu driver build sonucunu varsayılan olarak yerel Docker image store'a yüklemiyordu.

### Çözüm

Build komutuna `--load` parametresi eklendi:

```powershell
docker buildx build --load -t service-a:1.0 .
```

### Çıkardığım ders

Build işleminin başarılı olması, image'ın her zaman yerel image listesine yüklendiği anlamına gelmez.

Build driver ve output davranışı kontrol edilmelidir.
