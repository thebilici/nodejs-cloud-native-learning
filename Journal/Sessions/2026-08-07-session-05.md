```text

```

oldu.

# 2. Service A Deployment Dosyasını Oluşturdum

Service A'yı Kubernetes üzerinde çalıştırmak için:

```text
deployments/service-a-deployment.yaml
```

dosyasını oluşturdum.

Deployment içerisinde Service A için:

```yaml
replicas: 2
```

tanımladım.

Böylece Kubernetes'e Service A'dan 2 Pod çalışmasını istediğimi belirttim.

Pod'ları eşleştirmek için:

```yaml
app: service-a
```

label'ını kullandım.

Container tarafında:

```yaml
image: service-a:1.1
```

image'ını kullandım.

Son durumda Deployment'ın temel yapısı:

```yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: service-a

spec:
  replicas: 2

  selector:
    matchLabels:
      app: service-a

  template:
    metadata:
      labels:
        app: service-a

    spec:
      containers:
        - name: service-a
          image: service-a:1.1
          imagePullPolicy: IfNotPresent
```

şeklinde oldu.

# 4. Deployment Manifestini Test Ettim

Gerçek Deployment oluşturmadan önce manifesti kontrol ettim:


Daha sonra gerçek apply sırasında hata aldım.

---

# 5. Aldığım Hata

Deployment'ı oluştururken:

```powershell
kubectl apply -f .\deployments\service-a-deployment.yaml
```

komutunu çalıştırdım.

Şu hatayı aldım:

```text
Deployment in version "v1" cannot be handled as a Deployment:
strict decoding error:
unknown field "spec.containers"
```

Sorunun YAML içerisindeki hiyerarşiden kaynaklandığını fark ettim.

`containers` alanını Deployment'ın doğrudan `spec` alanına koymuştum.

Yanlış mantık:

```text
Deployment
└── spec
    └── containers
```

Doğru yapı:

```text
Deployment
└── spec
    └── template
        └── spec
            └── containers
```

Dosyayı düzelttikten sonra Deployment başarıyla oluşturuldu.

# 8. ReplicaSet'i İnceledim

Deployment oluşturduktan sonra Kubernetes'in arka planda oluşturduğu ReplicaSet'i kontrol ettim.

```powershell
kubectl get replicasets
```

Sonuç:

```text
NAME                   DESIRED   CURRENT   READY
service-a-58dbb9c969   2         2         2
```

Burada:

```text
DESIRED = 2
CURRENT = 2
READY   = 2
```

olduğunu gördüm.

Bu aşamada Deployment, ReplicaSet ve Pod arasındaki bağlantıyı daha net anladım:

```text
Deployment
    ↓
ReplicaSet
    ↓
Pod
    ↓
Container
```

Ayrıca Scheduler'ın Pod oluşturan yapı olmadığını öğrendim.

ReplicaSet gerekli Pod sayısının korunmasında görev alırken Scheduler oluşturulan Pod'un hangi Node üzerinde çalışacağına karar veriyor.

---

# 9. Desired State Mantığını Gördüm

Deployment içerisinde:

```yaml
replicas: 2
```

yazdığımda Kubernetes'e yalnızca bir kere:

```text
2 Pod oluştur
```

demediğimi fark ettim.

Aslında istediğim durum:

```text
Her zaman 2 Pod çalışıyor olsun.
```

Bu yüzden Pod'lardan biri kaybolursa sistem tekrar 2 Pod'a ulaşmaya çalışıyor.

Bu noktada Kubernetes'in tek tek Pod'ları korumaktan çok istenen sistemi koruduğunu anladım.

# 10. Service A İçin Kubernetes Service Oluşturdum

Pod'lara doğrudan IP üzerinden erişmenin doğru olmayacağını gördüm.

Çünkü Pod IP adresleri Pod yeniden oluşturulduğunda değişebilir.

Bu nedenle:

```text
deployments/service-a-service.yaml
```

dosyasını oluşturdum.

Manifest:

```yaml
apiVersion: v1
kind: Service

metadata:
  name: service-a

spec:
  selector:
    app: service-a

  ports:
    - port: 3000
      targetPort: 3000
```

şeklinde oldu.

Burada Service'in:

```yaml
selector:
  app: service-a
```

ile Service A Pod'larını bulmasını sağladım.

# 13. Cluster İçinden Gerçek HTTP Testi Yaptım

Service'in gerçekten çalıştığını görmek için cluster içerisinde geçici bir curl Pod'u oluşturdum:

```powershell
kubectl run curl-test --image=curlimages/curl --restart=Never --command -- sleep 3600
```

```powershell

```

Request başarılı şekilde cevaplandı.

Böylece aşağıdaki iletişimin gerçekten çalıştığını doğrulamış oldum:

```text
curl-test Pod
      ↓
service-a:3000
      ↓
Kubernetes Service
      ↓
Service A Pod
      ↓
Express
      ↓
HTTP Response
```

# 14. Bugün Yaptığım En Önemli Çıkarımlar

Bugünkü çalışma sonunda:

- Deployment ile uygulamanın istenen durumunu tanımladım.
- `replicas: 2` ile Service A'yı iki Pod olarak çalıştırdım.
- ReplicaSet'in Pod sayısının korunmasındaki rolünü gördüm.
- Scheduler'ın Pod'u oluşturmadığını, uygun Node seçtiğini öğrendim.
- Deployment `spec` ile Pod `template.spec` arasındaki farkı aldığım hata üzerinden öğrendim.
- Pod IP'lerinin kalıcı olmadığını gördüm.
- Bu nedenle Pod'lara doğrudan IP üzerinden bağlanmak yerine Service kullandım.
- Service'in `selector` ile uygun Pod'ları bulduğunu gördüm.
- `port` ile `targetPort` arasındaki ilişkiyi öğrendim.
- ClusterIP Service oluşturdum.
- Service'in arkasındaki Pod endpointlerini kontrol ettim.
- Cluster içerisinden `service-a:3000` adresine gerçek HTTP isteği gönderdim.
- Pod IP'leri değişse bile client'ın Service adını kullanmaya devam edebileceğini öğrendim.
