## Metrics Server

Metrics Server, Kubernetes cluster içerisindeki resource metric'lerini toplamak için kullanılan bir component'tir.

Temel olarak:

```text
CPU
Memory
```

kullanım bilgilerini Kubernetes'e sağlar.

Metrics Server tam kapsamlı bir monitoring sistemi değildir.

Ana amaçlarından biri Kubernetes'in autoscaling mekanizmalarına resource metric sağlamaktır.

Basitleştirilmiş çalışma yapısı:

```text
Pods
↓
Nodes
↓
Kubelet
↓
Metrics Server
↓
Metrics API
↓
kubectl top / HPA
```

Metrics Server Node'lardaki Kubelet'lerden metric bilgilerini toplar.

Bu bilgiler Kubernetes Metrics API üzerinden kullanılabilir hale gelir.

## Kubernetes CPU Birimi

Kubernetes CPU değerlerinde:

```text
m = millicore
```

kullanılır.

Temel dönüşüm:

```text
1000m = 1 CPU Core
500m  = 0.5 CPU Core
100m  = 0.1 CPU Core
```

Örneğin:

```text
3m
```

çok düşük CPU kullanımını gösterirken:

```text
402m
```

yaklaşık `0.402 CPU Core` kullanımını ifade eder.

## Resource Management

Kubernetes resource yönetiminde üç kavramı birbirinden ayırdım:

```text
Request
Usage
Limit
```

Mental model:

```text
Request
→ Container için talep edilen resource

Usage
→ Container'ın gerçekten kullandığı resource

Limit
→ Container'ın kullanabileceği üst sınır
```

## Resource Request

Request, container'ın ihtiyaç duyduğu resource miktarını Kubernetes'e bildirir.

Service A için:

```yaml
requests:
  cpu: "100m"
  memory: "64Mi"
```

tanımladım.

`100m` CPU request olması container'ın sürekli `100m` CPU kullanacağı anlamına gelmez.

Örneğin:

```text
Request = 100m
Usage   = 3m
```

olabilir.

Scheduler Pod'ları Node'lara yerleştirirken request değerlerini dikkate alır.

## Resource Limit

Limit container'ın kullanabileceği resource için üst sınır tanımlar.

Service A için:

```yaml
limits:
  cpu: "500m"
  memory: "256Mi"
```

kullandım.

CPU limit ve memory limit aynı davranışı göstermez.

CPU tarafında limit nedeniyle throttling görülebilir.

Memory limit aşılırsa container OOM nedeniyle sonlandırılabilir.

## Service A Resource Configuration

Deployment içerisine eklediğim yapı:

```yaml
resources:
  requests:
    cpu: "100m"
    memory: "64Mi"
  limits:
    cpu: "500m"
    memory: "256Mi"
```

Böylece Service A için:

```text
CPU Request    = 100m
CPU Limit      = 500m

Memory Request = 64Mi
Memory Limit   = 256Mi
```

tanımlandı.

## CPU Request ve HPA

CPU request değeri HPA açısından da önemlidir.

Bizim değerlerimiz:

```text
CPU Request = 100m
HPA Target  = 50%
```

Örneğin ortalama CPU kullanımı:

```text
50m
```

olursa yaklaşık:

```text
50m / 100m × 100
=
50%
```

CPU utilization oluşur.

Kullanım:

```text
200m
```

olursa utilization yaklaşık:

```text
200%
```

olabilir.

Bu nedenle HPA çıktısında `%100` üzerinde CPU utilization görmek mümkündür.

## Horizontal Scaling

Horizontal Scaling instance sayısının değiştirilmesidir.

Örneğin:

```text
2 Pod
↓
3 Pod
↓
5 Pod
```

horizontal scale-up'tır.

Tersi:

```text
5 Pod
↓
3 Pod
↓
2 Pod
```

horizontal scale-down'dır.

Vertical Scaling ise instance sayısını değil mevcut instance'ın resource kapasitesini değiştirir.

Temel ayrım:

```text
Horizontal Scaling
→ Pod sayısını değiştir

Vertical Scaling
→ Pod'un resource kapasitesini değiştir
```

## Horizontal Pod Autoscaler

Horizontal Pod Autoscaler:

```text
HPA
```

olarak kısaltılır.

HPA metric değerlerine göre workload replica sayısını otomatik olarak değiştirebilir.

Bizim HPA:

```text
Deployment/service-a
```

üzerinde çalışıyor.

Configuration:

```text
Metric      = CPU
Target      = 50%
Min Replica = 2
Max Replica = 5
```

## HPA Çalışma Mantığı

Basitleştirilmiş yapı:

```text
Service A Pods
↓
CPU Usage
↓
Metrics Server
↓
HPA
↓
CPU Target karşılaştırması
↓
Deployment Replica Count
↓
ReplicaSet
↓
Pods
```

HPA doğrudan Pod oluşturmaz.

HPA Deployment'ın replica sayısını değiştirir.

Deployment ve ReplicaSet gerekli Pod'ların oluşturulmasını sağlar.

## HPA Manifesti

Service A için oluşturduğum HPA:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler

metadata:
  name: service-a-hpa

spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: service-a

  minReplicas: 2
  maxReplicas: 5

  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
```

Buradaki:

```yaml
scaleTargetRef:
```

HPA'nın hangi workload'u yöneteceğini belirler.

Bizim hedefimiz:

```text
Deployment/service-a
```

oldu.

## Replica Sınırları

HPA içerisinde:

```yaml
minReplicas: 2
maxReplicas: 5
```

kullandım.

Bu nedenle Service A:

```text
Minimum = 2 Pod
Maximum = 5 Pod
```

arasında scale edilebilir.

CPU çok düşük olsa bile HPA 2 Pod'un altına düşmez.

CPU çok yüksek olsa bile 5 Pod'un üzerine çıkmaz.

## HPA Target

CPU hedefini:

```yaml
averageUtilization: 50
```

olarak belirledim.

Bu Service A Pod'larının CPU request değerlerine göre hesaplanan ortalama utilization için hedef değerdir.

## Scale-Up Akışı

Test sırasında oluşan süreç:

```text

↓
/work request sayısı artar
↓

↓

↓
HPA target'ın aşıldığını görür
↓
Desired replica artar
↓
Deployment scale edilir
↓

```

Bu şekilde HPA'nın çalışma mantığını uygulamalı olarak gözlemledim.

## Yeni Pod'ların Durumu

Scale-up sırasında:

```powershell
kubectl get pods
```

komutunu kullandım.

Yeni Pod'larda sırasıyla:

```text
0/1 Pending
↓
0/1 Running
↓
1/1 Running
```

durumlarını gözlemledim.

Burada önemli ayrım:

```text
Running
≠
Ready
```

Pod çalışmaya başlamış olabilir fakat Readiness Probe henüz başarılı olmamış olabilir.

Readiness başarılı olduktan sonra Pod trafiğe hazır hale gelir.

## Scale-Down

Stress testi bittiğinde yük azaldı.

CPU utilization:

```text
3% / 50%
```

seviyesine kadar düştü.

Ancak HPA Pod sayısını hemen:

```text
5 → 2
```

yapmadı.

Bir süre bekledikten sonra replica sayısı tekrar minimum seviyeye indi.

Bu davranış scale-down stabilization ile ilişkilidir.

Amaç gereksiz replica dalgalanmasını azaltmaktır.

## HPA Conditions

Üç önemli condition gördüm:

```text
AbleToScale
ScalingActive
ScalingLimited
```

### AbleToScale

```text
AbleToScale = True
```

HPA'nın scaling işlemi gerçekleştirebilir durumda olduğunu gösterir.

### ScalingActive

```text
ScalingActive = True
ValidMetricFound
```

HPA'nın geçerli CPU metric'ine erişebildiğini ve replica hesabı yapabildiğini gösterir.

### ScalingLimited

```text
ScalingLimited = False
DesiredWithinRange
```

hesaplanan replica sayısının belirlediğimiz sınırlar içerisinde olduğunu gösterir.

## HPA Events

Events bölümünde:

```text
SuccessfulRescale
```

event'lerini gördüm.

CPU target'ın üzerine çıktığında:

```text
cpu resource utilization
above target
```

nedeniyle replica sayısı artırıldı.

Metric'ler target'ın altına düştüğünde:

```text
All metrics below target
```

nedeniyle replica sayısı azaltıldı.

Böylece HPA'nın scaling geçmişini event'lerden de doğruladım.
